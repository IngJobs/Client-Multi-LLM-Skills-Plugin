# 플러그인·스킬 작성

Client-Multi-LLM-Skills-Plugin 저장소의 새 플러그인·스킬 생성과 기존 본문·참조·설정 수정을 수행합니다. 일반 프로젝트의 코드 작업이나 사용자 전역 플러그인 설정 관리에는 적용하지 않습니다.

## 작업 대상 확인

- 사용자 요청과 현재 작업공간에서 대상 저장소 및 추가·수정 범위를 확인합니다. 저장소 위치가 불명확하면 질문하고 답변을 기다립니다.
- 대상 저장소의 프로젝트 지침과 README, `scripts/add_skill.py`, `scripts/generate_manifests.py`, 관련 `plugin-config.json`을 읽습니다. 아래 명령과 경로는 모두 대상 저장소 루트 기준이며, 설치된 이 스킬의 캐시 경로를 작업 저장소로 사용하지 않습니다.
- 현재 Git 변경을 확인하고 기존 사용자 변경을 보존합니다. 플랫폼·플러그인·스킬 이름은 요청과 기존 구조에서 정하고, 결과에 영향을 주는 요구사항이 빠졌을 때만 질문합니다.
- 파일 읽기·검색·셸 실행·질문은 현재 호스트의 제공 기능으로 수행합니다. 질문 도구가 없으면 대화로 묻고 실제 답변을 기다립니다. 이 스킬 자체에는 MCP나 형제 스킬이 필요하지 않습니다.

## 생성 또는 기존 파일 수정

새 플러그인이나 새 스킬은 저장소의 생성 스크립트를 사용합니다. Python 3.9 이상이 필요하며 추가 패키지는 필요하지 않습니다. 플랫폼·플러그인·스킬 이름은 소문자와 숫자, 단어 사이 하이픈으로 구성하고 64자 이내로 정합니다.

```sh
python3 scripts/add_skill.py \
  --platform shared \
  --plugin example-plugin \
  --skill example-guide \
  --description "이 스킬을 사용하는 구체적인 요청과 목적"
```

예시 값을 실제 작업에 맞게 바꿉니다. 기존 플러그인 이름을 사용하면 새 스킬만 추가하며, 기존 설정과 스킬은 덮어쓰지 않습니다. 이미 존재하는 스킬을 수정할 때는 생성기를 다시 실행하지 않고 해당 파일을 편집합니다.

생성기는 `plugins/<platform>/<plugin>/plugin-config.json`, 스킬 템플릿, 대상 CLI의 매니페스트와 공용 카탈로그를 만듭니다. 생성된 SKILL.md의 작성 중 안내를 실제 절차로 교체합니다. 기존 스킬을 이식할 때는 사용자가 허용한 내용 변경 범위와 패키징 변경 범위를 구분해 지킵니다.

## 본문과 참조 작성

- SKILL.md의 `name`은 스킬 폴더명과 맞추고, `description`에는 사용자가 어떤 요청을 할 때 이 스킬을 사용하는지 적습니다. 본문에는 목적·필수 절차·판단 기준·완료 조건을 둡니다.
- 여러 CLI가 공유하는 본문은 특정 호스트의 도구명·스킬 설치 경로·호출 문법을 고정하지 않습니다. 필요한 기능과 입력 의도를 설명하고, 실제 도구 스키마와 설치 위치를 확인해 사용하도록 합니다. CLI별 사용자 호출 예시는 README에서 관리합니다.
- 상세 업무 절차·템플릿 등 필요한 자료만 해당 스킬의 `references/`에 둡니다. 별도 실행 지침이 필요하면 `references/execution-environment.md`로 분리하고 SKILL.md에서 읽을 시점을 안내합니다. 짧은 스킬에 불필요한 참조 파일을 만들지 않습니다.
- 상대 링크는 링크가 있는 파일 기준으로 작성합니다. 개별 플러그인 설치 시에도 필요한 자료가 포함되도록 하며, 설치본 밖의 저장소 파일을 고정 상대 링크로 참조하지 않습니다. 이 스킬처럼 작업 대상 저장소의 파일을 읽어야 한다면 작업공간에서 그 저장소를 먼저 확인하도록 안내합니다.
- 형제 스킬이 필요하면 실제 설치 위치에서 읽도록 안내하고, 미설치 시 가능한 범위와 중단되는 단계를 정합니다. MCP 사용 시에는 연결·인증 전제와 기능을 명시합니다. 사용할 수 없는 도구를 호출한 것으로 처리하거나 기본 선택값을 사용자 동의로 간주하지 않습니다.
- 사용자가 요청한 업무 규칙·산출물·승인 범위를 유지합니다. 작성 요청만으로 커밋·푸시·설치·외부 게시까지 수행하지 않습니다.

## 패키징 설정

플러그인 정보는 `plugin-config.json`, 마켓플레이스 공통 정보는 `marketplace-metadata.json`에서 관리합니다. 생성된 `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`, `gemini-extension.json`, `.claude-plugin/marketplace.json`은 직접 수정하지 않습니다.

- 설명·작성자·버전·대상 CLI를 확인합니다. 새 플러그인은 생성기의 초기 버전을 사용하고, 기존 플러그인을 배포하는 작업이면 해당 버전을 올립니다.
- `targets`에는 지원할 CLI를 지정합니다. 생성기는 특정 CLI 전용 본문·도구·에이전트를 다른 환경으로 변환하지 않으므로, 매니페스트 생성만으로 실행 호환성을 단정하지 않습니다.
- 필요한 플러그인은 `dependencies`에 기록합니다. CLI별 차이가 있으면 README의 설정 규칙과 생성기가 지원하는 형식을 확인합니다. 필수 의존성과 선택적 연동을 구분하며, Codex·Gemini가 의존성을 자동 설치한다고 가정하지 않습니다.
- CLI별 추가 설정은 공통 설정의 `claude`·`codex`·`gemini` 객체를 사용합니다. 스킬 본문은 공유하며, 별도의 CLI별 복사본을 만들지 않습니다.

설정 변경 후 저장소 루트에서 생성 명령을 실행합니다.

```sh
python3 scripts/generate_manifests.py
```

## 검증과 완료 보고

```sh
python3 scripts/generate_manifests.py --check
python3 -m unittest discover -s tests
git diff --check
```

변경 diff에서 사용자 요청 범위, 템플릿 잔여 문구, 참조 링크, 생성 파일과 설정의 일치를 확인합니다. 정적 검사는 실제 CLI 설치·스킬 활성화·MCP 호출의 성공을 증명하지 않습니다. 실행 검증을 했다면 사용한 환경과 실제 확인한 범위를 구분해 보고합니다.

사용자에게 변경한 플러그인·스킬, 검사 결과, 남은 제한을 알립니다. PR에 포함할 파일은 본문·참조·원본 설정·생성 결과이며, PR 생성이나 커밋·푸시는 해당 요청이 있을 때 수행합니다. README는 설치·호출·공통 작성 안내에 영향을 주는 변경만 반영하고 개별 작업 기록은 넣지 않습니다.
