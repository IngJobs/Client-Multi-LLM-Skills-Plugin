# Teamblind Android — 작업 플래닝 문서 작성 (task-planning)

`task-planning <티켓키>` 를 지정해 요청하거나 "플래닝 해줘"·"플래닝 문서 정의해줘" 류 요청 시 자동 발동되는 스킬입니다. 참고 자료(기획서·Figma·Jira·타 플랫폼 스펙·GitHub 링크)를 수집하고 **코드베이스를 전수조사**해, 팀 표준 양식의 **플래닝 문서**를 작성합니다.

> **이 스킬을 실행할 때는 반드시 [references/workflow.md](references/workflow.md) 의 업무 절차·조사 요령·문서 템플릿을 따라야 합니다. 도구 호출 형태는 실행 환경에 맞게 대응합니다.** 이 SKILL.md 는 그 절차가 따르는 컨벤션의 단일 출처(canonical)이고, workflow.md 는 실행 정본입니다 — 둘을 함께 열어 두고 진행하십시오.

> **이 문서는 "무엇을 왜 하는가"를 합의하는 문서입니다.** 세부 구현 계획은 Task 착수 시점에 Task 단위로 따로 세웁니다 — 여기서는 방향만 잡습니다.

---

실행 전에 [실행 환경 지침](references/execution-environment.md)을 읽고, 현재 환경에 맞는 도구·질문·스킬 참조 방식을 적용합니다.

## 입력

모두 선택 입력이며, **요구사항 출처가 최소 1개**는 있어야 합니다 (없으면 사용자에게 요청).

| 입력 | 형태 | 용도 |
|---|---|---|
| Jira 티켓 | 키(`TB-1234`) 또는 링크 | 요구사항·정책 표의 1차 출처. 정규식 `[A-Z]{2,}-\d+` 로 추출 |
| 기획서 | 문서 링크(Confluence 등)·파일·본문 붙여넣기 | 정책/요구사항 정의 |
| Figma 디자인 | Figma URL | UI 스펙. **수치(패딩·마진·간격)는 `get_metadata` 로 직접 실측** — 추정 금지 |
| 타 플랫폼 스펙 | 타 플랫폼 스펙 문서·본문 | **교차검증** 대상 — 게이트 방식·플래그명·정책 확정 사항의 불일치 표면화 |
| 기타 문서 | API 스펙, 정책 문서 등 | 서버 계약 확인 |
| GitHub 링크 | PR·브랜치·커밋 | 선행/연관 작업 파악 |

- 입력이 부족해 판단이 갈리는 지점(정책 해석·UX 결정 등)은 추측으로 메우지 않고 **문서의 "확인 사항" 항목으로 명시**합니다.

## 산출물

- **`<티켓키>-planning.md`** — 앱 레포 루트에 생성 (예: `TB-10169-planning.md`)
- 문서는 **Task 구조가 기본**입니다 — 작업이 하나여도 `전체 Task 요약` + `Task 1` 로 씁니다 (아래 "Task 구조" 참조). 문서는 하나로 유지합니다.
- 접어두는 섹션은 **접기 마커**로 표기합니다 (아래 "접기 마커" 참조).
- 작성 후 요약과 함께 사용자 검토를 받고, 피드백을 반영해 갱신합니다. **문서 작성이 이 스킬의 끝**이며, 승인 없이 구현 코드를 작성하지 않습니다.
- 문서 확정 후 **Jira 본문 업로드를 제안**할 수 있습니다 (옵션 — 8단계, 사용자 동의 시에만 실행).

## 문서 양식 (팀 표준)

섹션 순서는 "읽는 사람의 질문 순서"를 따릅니다: 무엇이 문제 → 무얼 하나/안 하나 → 서버와 뭘 주고받나 → 어떻게 쪼개나 → 각 Task 는 무슨 얘기인가 → 얼마나 걸리나.

| 섹션 | 접기 | 내용 |
|---|----|---|
| 참고 자료 |    | JIRA·기획서·Figma·기준 문서 링크 표 |
| 문제 정의 |    | **기획 개요 → 이번 작업의 방향 → 현재 동작 → 문제** (요약+하위 bullet) + **정책 ↔ 구현 주체(서버/클라) 표** |
| 목표 |    | 클라가 실제로 하는 일만. 항목당 1~2줄 |
| 비목표 | **접기** | 안 하는 일 + 왜 안 해도 되는지 한 줄 근거 — 리뷰어의 "이건 왜 없지?"에 선답 |
| API 설계 |    | 신규/변경 엔드포인트, 요청·응답 **JSON 예시**(표 아님), **하위호환 기본값 방향**. 미확정은 확인 사항으로 |
| 전체 Task 요약 |    | Task · 내용 요약 · 의존 표 + Task 경계 원칙 1~2문장. **일정 열 없음** |
| Task N — 이름 |    | **Task 개요 → 작업 범위(맥락 위주) → 개발 방향** |
| └ 위험 요소 | **접기** | 그 Task 에 해당하는 위험만 Task 안에 둔다 — 독립 섹션으로 빼지 않음 |
| 확인 사항 | **접기** | 서버·웹·디자인 확인 항목 `- [ ]` 체크리스트 |
| 테스트 계획 | **접기** | 시나리오 × 케이스별 기대 결과 표. **회귀·하위호환 행 필수** |
| 예상 일정 |    | **표 없이** 총 일정 한 줄 + 크리티컬 패스 1~2문장. Task별 공수 분해 금지 |

상세 템플릿 전문은 [workflow.md](references/workflow.md) **6단계** 참조.

### 본문 서술 구조 (문제 정의 · Task 설명)

확인한 내용을 줄글로 늘어놓지 않습니다. 두 섹션의 본문은 **"요약 한 줄 + 하위 들여쓰기 bullet"** 구조로 씁니다 — 리뷰어가 요약만 훑고 필요한 곳만 펼쳐 읽을 수 있게 하기 위함입니다. (PR 본문 Abstract 규칙과 동일한 방식 — `generate-pr-auto` skill 참조)

- **상위 라인에는 고유명사 금지** — 클래스명·플래그명·Path명 같은 식별자는 **하위 bullet 으로 격리**합니다.
- 요소 라벨은 굵게, 각 요소는 `- 요약:` 한 줄로 시작하고 세부는 한 단계 들여씁니다.
- **권장 구조이며 고정이 아닙니다** — 실제로 확인된 요소만 씁니다. 한두 문장으로 끝나는 단순한 내용은 2~3문장 단락 서술을 허용합니다(길어지면 나눔).
- **기획 개요는 최소 맥락만** — 이번 기획이 무엇을 만들려는지 한 줄 + 유저 흐름 1~2개면 충분합니다. 기획서를 옮겨 적지 않습니다.
- **이번 작업의 방향은 한 줄 결론만** 씁니다. 왜 그 방향인지는 뒤의 현재 동작·문제가 받치므로 여기서 근거를 늘어놓지 않습니다.
- **갈렸던 지점·기각한 대안은 개발 방향의 하위 bullet 으로** 넣습니다 (별도 요소로 빼지 않음).

| 섹션 | 권장 요소 (이 순서) |
|---|---|
| 문제 정의 | **기획 개요** → **이번 작업의 방향** → **현재 동작** → **문제** |
| Task 설명 | **Task 개요** → **작업 범위**(맥락 위주) → **개발 방향** |

```markdown
**개발 방향**

- 요약: <어떤 방향으로 구현하는지 한 줄 — 고유명사 없이>
  - `<핵심 클래스명>`: <그 안에서 하는 일>
  - <택하지 않은 대안과 기각 사유 — 갈렸던 지점이 있을 때만>
```

### Task 구조

**Task = 독립 머지 단위** (브랜치/PR 1개). 절반만 머지돼도 앱이 정상 동작하는 경계로 자릅니다.

- 문서 최상단 가까이에 `전체 Task 요약` 표(Task · 내용 요약 · 의존)를 두고, 이어서 `Task 1`, `Task 2` … 섹션을 씁니다.
- 나눌 기준: 독립적으로 머지/배포 가능한 단위 / 서버 선배포 등 순서 의존 / PR 하나로 리뷰하기 부담스러운 규모.
- Task 간 **의존과 순서**(선행 Task·서버 선배포 등)를 요약 표에 명시합니다.
- Jira 하위 태스크가 있으면 Task ↔ 티켓 매핑을 함께 기재합니다.
- **Task별 예상 공수는 쓰지 않습니다** — 일정은 문서 마지막에 총계로만.

### 접기 마커

접어두는 섹션은 아래 마커로 감쌉니다. GitHub·IDE 미리보기에서 실제로 접히고, 8단계에서 Jira 로 올릴 때 `update-jira-description` 스킬이 **Jira 접기(ADF expand)로 변환**합니다.

```markdown
# 비목표

<details><summary>비목표 (클라 작업 없음)</summary>

- **<항목>** — <왜 안 해도 되는지 한 줄>

</details>
```

- **접기 블록 바로 위에 대응하는 헤딩을 둡니다.** 접힌 상태에서도 문서 아웃라인에 섹션이 보이게 하기 위함이며, Jira 로 올려도 헤딩은 접기 밖에 그대로 남습니다.
  - `summary` 는 **헤딩 이름을 그대로 담되 이모지·괄호 부가 문구는 붙여도 됩니다** — `# 비목표` ↔ `비목표 (클라 작업 없음)`, `## 위험 요소` ↔ `⚠️ 위험 요소` 처럼. 헤딩과 무관한 이름을 새로 짓지는 않습니다.
- 마커 안팎으로 **빈 줄 필수**. 중첩 금지(1단계만). 표 셀 안에는 넣지 않습니다.
- 마커 문법의 단일 출처는 `update-jira-description` skill 의 SKILL.md §접기(expand) 지원 입니다 — 문법이 바뀌면 그쪽을 먼저 봅니다.
  - **선행 조건** — 그 skill 의 접기 지원이 함께 설치돼 있어야 합니다. 지원하지 않는 버전에서는 마커가 변환되지 않고 원문 그대로 올라갑니다.

## 작성 원칙 (절대 준수)

1. **판단은 코드로, 표기는 클래스명으로** — "클라 작업 필요/불필요" 는 전부 실제 코드를 열어 확인한 뒤 씁니다. 다만 **문서에는 파일 경로·라인 번호를 쓰지 않습니다.** 핵심 클래스명만 적고, 근거는 조사 과정에 남겨 리뷰 질문이 나올 때 답합니다. 기획서·티켓 문구만 보고 작업 유무를 단정하지 않습니다.
2. **서버/클라 책임 구분이 문서의 뼈대** — "X를 Y에게 노출/차단" 류 정책은 기본적으로 서버 리스트 필터링·API 에러 책임입니다. 클라 작업은 클라에 하드코딩된 차단/게이트 지점만 잡습니다. **범위 부풀리기 금지.**
3. **비목표에 근거를 남긴다** — 조사했지만 작업이 아닌 것으로 판명된 항목은 버리지 않고 비목표(접기)에 한 줄 근거와 함께 기록합니다 (재조사 방지 + 범위 논쟁 시 결정 기록).
4. **게이트/조건 완화 시 하위 표면 전수 재조사** — 진입 조건이 암묵적으로 보호하던 내부 UI(작성 버튼·메뉴 등)가 무방비로 노출되는지 반드시 확인합니다. 해당 네비게이션 Path 의 **호출처 전수 검색**이 기본 동작입니다.
5. **타 플랫폼 스펙과 교차검증** — 스펙이 주어지면 게이트 메커니즘·신설 필드명·정책 확정 사항·차단 UX 방식의 일치 여부를 대조합니다. 문서는 Android 작업을 쓰는 문서이므로 **대조 자체를 옮겨 적지 않고**, Android 판단이 달라지는 부분만 해당 Task 설명이나 확인 사항에 담습니다.
6. **맥락 우선, 코드 스니펫은 필요한 곳에만** — Task 설명은 "왜 이 구조인지, 무엇이 바뀌는지"를 일상어로 씁니다. 코드 스니펫이 금지는 아닙니다 — 기본은 생략하되, **특이한 구조이거나 코드를 봐야 판단이 서는 지점**(조건 방향이 반전되는 치환, 기존 계약과 다른 시그니처 등)은 몇 줄짜리로 짧게 붙입니다. 길게 붙여넣거나 구현 순서를 코드로 나열하지는 않습니다 — 상세 구현은 Task 착수 시점의 별도 플래닝 몫입니다.
7. **단순 모델 생성은 설명 생략** — 비즈니스 로직이 없는 DTO·Entity·VO·UiState 신설은 서술하지 않고 작업 표 한 줄로 갈음합니다. 변환 규칙이나 기본값 결정처럼 **판단이 들어간 부분만** 문장으로 설명합니다.
8. **신설 플래그는 기본값 방향을 명시** — fail-closed(default false)/fail-open 선택과 그에 따른 배포 순서 의존(서버 선배포 등)을 해당 Task 의 위험 요소(접기)에 기재합니다.
9. **기존 패턴 미러링** — 신규 파이프라인(config 필드→Authenticator/UseCase 등)은 코드베이스의 기존 동일 패턴을 참조 클래스명으로 명시해 구현 방향을 고정합니다.
10. **표준 양식을 벗어나지 않는다** — 「문서 양식」 표에 없는 섹션은 임의로 추가하지 않습니다. 이번 티켓에 필요해 보이면 그때마다 사용자 질문으로 묻고, 동의를 받은 경우에만 넣습니다 — 왜 필요한지와 어느 위치에 넣을지를 함께 제안합니다.
11. **사람이 읽는 문서다** — 클래스명·플래그명·Path명을 본문 문장에 남발하지 않습니다. 문장은 "무엇이 왜 바뀌는지"를 설명하고, 고유명사는 표의 참조 열이나 괄호로 내립니다. **나열이 3개 이상이면 표**, 논리 전개는 짧은 단락, 종속 관계는 들여쓰기, 섹션 사이는 구분선. 문제 정의·Task 설명의 본문 구조는 §본문 서술 구조 를 따릅니다.
12. **문체는 명사형 종결** — 산출 문서의 문장은 "~합니다/~입니다" 가 아니라 **"~함 / ~했음 / ~임"** 으로 끝냅니다. 표 셀·목록 항목도 동일합니다 (예: "게이트를 교체합니다" → "게이트 교체함", "코드 확인 결과 작업이 필요하지 않습니다" → "코드 확인 결과 작업 불필요함"). 이 규칙은 **문서에만** 적용되고, 사용자에게 보고하는 대화 문장에는 적용하지 않습니다.

## 실행 절차

`task-planning <티켓키>` 호출 또는 "플래닝 해줘" 요청 시 아래 0~8단계를 순서대로 수행합니다.

> ⚠️ **이 스킬을 실행할 때는 반드시 [references/workflow.md](references/workflow.md) 의 0~8단계 절차를 그대로 따릅니다.** 아래 표는 요약이며, 각 단계의 기능별 도구 사용법·조사 요령·문서 템플릿은 workflow.md 가 정본입니다. 단계를 건너뛰거나 순서를 바꾸지 말고, 문서 작성 전 반드시 workflow.md 를 먼저 읽으십시오.

| 단계 | 내용 |
|---|---|
| 0 | 도구 사전 준비 — 실행 환경에 따라 필요한 질문·조회·실행 기능의 가용성 확인 |
| 1 | 입력 수집 — 티켓 키 추출·확인, 제공된 자료 목록화, 요구사항 출처 없으면 요청 |
| 2 | 자료 읽기 — Jira 본문, 기획서, Figma(수치 실측), 타 플랫폼 스펙, GitHub 링크 |
| 3 | 정책 → 책임 구분 — 정책 항목별 서버/클라 구현 주체 표 초안 |
| 4 | 코드베이스 전수조사 — 영향 지점·게이트·기존 패턴 확정(조사 메모엔 file:line, 문서엔 클래스명), 하위 표면 재조사 |
| 5 | 교차검증 (타 플랫폼 스펙 제공 시) — 충돌 항목 도출·반영 |
| 6 | 문서 작성 — `<티켓키>-planning.md`, 표준 양식·작성 원칙·Task 구조·접기 마커 적용 |
| 7 | 사용자 검토 — 요약 보고 후 피드백 반영 (승인 전 구현 시작 금지) |
| 8 | (옵션) Jira 본문 업로드 제안 — 문서 확정 후 `update-jira-description` skill 로 업로드할지 질문, **동의 시에만** 실행 (접기 마커는 Jira 접기로 변환됨) |
