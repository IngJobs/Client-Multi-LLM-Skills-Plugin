# 작업 플래닝 문서 작성 (task-planning) — 상세 실행 절차

`task-planning` 스킬이 따르는 **단계별 실행 절차**입니다. 참고 자료를 수집·정독하고, 코드베이스를 전수조사해 서버/클라 책임을 가른 뒤, 팀 표준 양식의 플래닝 문서를 작성하고 사용자 검토를 받습니다.

> 문서 양식·작성 원칙 등 **컨벤션 정의는 `SKILL.md` 를 단일 출처**로 참조합니다. 이 문서는 그 컨벤션을 적용하는 정확한 도구 명령·조사 요령·템플릿 전문만 정의합니다.

> **MCP 도구 표기**: 아래 예시는 팀 표준 alias(`mcp__jira__*`, `mcp__figma-desktop__*`)로 표기합니다. 실제 도구 id 는 개인 MCP 설정에 따라 다를 수 있으므로, **0단계에서 `ToolSearch` 로 이름이 아닌 기능(이슈 조회/디자인 메타데이터/스크린샷)으로 스키마를 로드**해 표기 불일치로 실패하지 않게 합니다.

---

## 목차

- **워크플로우 (0~8단계)** — 0 도구 사전 준비 · 1 입력 수집 · 2 자료 읽기 · 3 정책→책임 구분 · 4 코드베이스 전수조사 · 5 교차검증 · 6 문서 작성 · 7 사용자 검토 · 8 (옵션) Jira 본문 업로드
- **문서 템플릿 전문**
- **품질 기준**
- **주의사항**

## 워크플로우

### 0단계 — 도구 사전 준비

시스템 리마인더의 deferred tools 목록을 확인하고, 이번 실행에서 쓸 도구가 미로드 상태면 `ToolSearch` 로 로드합니다.

- `mcp__jira__getJiraIssue` — 티켓 본문·필드 조회 (1·2단계)
- `mcp__jira__getConfluencePage` / `mcp__jira__fetch` — 기획서가 Confluence 링크일 때 (2단계)
- `mcp__figma-desktop__get_metadata` · `get_screenshot` · `get_design_context` — Figma 실측 (2단계)
- `WebFetch` — 일반 웹 문서 링크 (2단계)
- `AskUserQuestion` — 입력 요청·판단 갈림 확인·Jira 업로드 여부 질문 (1·7·8단계)

GitHub 링크는 `gh` CLI(`gh pr view`, `gh pr diff`)를 기본으로 사용합니다.

### 1단계 — 입력 수집

1. 발화·인자에서 **Jira 티켓 키** 추출: 정규식 `[A-Z]{2,}-\d+`. 링크(`…atlassian.net/browse/TB-1234`)에서도 추출.
2. 제공된 자료를 유형별로 목록화: 기획서 / Figma / 타 플랫폼 스펙 / 기타 문서 / GitHub 링크.
   - 사용자가 본문을 직접 붙여넣은 경우는 그 자체가 자료입니다 — 링크를 다시 요구하지 않습니다.
3. **요구사항 출처가 하나도 없으면** 사용자에게 요청하고 중단합니다. 티켓 키만 있으면 Jira 본문을 1차 출처로 사용합니다.
4. 산출물 파일명 확정: `<티켓키>-planning.md` (티켓이 없으면 사용자에게 slug 를 확인).
5. **조사 대상 레포 확인** — 4단계 전수조사와 6단계 산출물 위치가 앱 레포(android_v2)를 전제하므로 여기서 확인합니다. 이 스킬은 플러그인 레포·문서 레포에서도 호출될 수 있고, 그 경우 조사가 대상 코드를 찾지 못한 채 "클라 작업 없음" 으로 기울어 **조사 실패가 조용한 오답이 됩니다**.

   ```bash
   git rev-parse --show-toplevel                                  # 현재 레포 루트
   test -f app/config/version.properties && echo "앱 레포" || echo "앱 레포 아님"
   ```

   - 앱 레포면 그대로 진행하고, `SWEEP_ROOT`(조사 대상)·`DOC_DIR`(문서 저장 위치)을 레포 루트로 둡니다.
   - 앱 레포가 **아니면** `AskUserQuestion` 한 번으로 (a) 전수조사 대상 경로 (b) 문서 저장 위치를 함께 묻고, **답을 받기 전에는 4단계로 넘어가지 않습니다.** 현재 디렉터리를 임의로 조사해 결론내지 않습니다.
   - 식별 파일 `app/config/version.properties` 는 같은 계열 `generate-pr-auto` 가 릴리즈 버전 소스로 쓰는 것과 동일합니다.

### 2단계 — 자료 읽기

**Jira 티켓**:

```
mcp__jira__getJiraIssue(cloudId="teamblind.atlassian.net", issueIdOrKey="<티켓키>",
  fields=["summary","description","issuetype","status","parent","fixVersions"],
  responseContentFormat="markdown")
```

- description 의 정책 표·요구사항을 원문 그대로 확보 (요약본으로 대체하지 않음)
- 실패 시 `getAccessibleAtlassianResources` 로 cloudId 재조회

**기획서·기타 문서**: Confluence 는 `getConfluencePage`, 일반 웹은 `WebFetch`, 로컬 파일은 `Read`.

**Figma** (제공 시):

- 화면 구조는 `get_metadata` / `get_design_context`, 시각 확인은 `get_screenshot`
- **패딩·마진·간격 등 수치는 `get_metadata` 의 좌표에서 직접 계산**해 확인합니다. 사용자 발화나 눈대중으로 수치를 적지 않습니다. 문서에는 필요한 수치만 남기고, 화면 조립 세부는 Task 착수 시점 플래닝으로 넘깁니다.

**GitHub 링크**:

```bash
gh pr view <번호|URL> --json title,body,files   # 선행 작업 파악
gh pr diff <번호|URL>                            # 변경 내용 확인 (필요 시)
```

**API 스펙 자료**: 신규/변경 엔드포인트 후보, 요청·응답 필드, 기존 API 재사용 여부(확장 vs 신설)를 뽑아 6단계 **API 설계** 섹션의 입력으로 만듭니다. 미확정 항목은 확인 사항 후보로 적어둡니다.

**타 플랫폼 스펙**: 다음 항목을 뽑아 5단계 교차검증 입력으로 만듭니다 —
① 게이트/차단 메커니즘(서버 플래그명 vs 클라 하드코딩) ② 신설 서버 필드명·기본값 ③ 등급/케이스별 정책 확정 사항(특히 "변경하지 않음"으로 못박은 비목표) ④ 차단 UX 방식(사전 차단 vs 사후 에러) ⑤ 테스트 계획의 회귀 항목.

### 3단계 — 정책 → 책임 구분 (표 초안)

자료의 정책 항목을 한 줄씩 분해해 **구현 주체**를 배정합니다.

| 정책 유형 | 기본 배정 |
|---|---|
| 특정 대상에게 콘텐츠 노출/미노출·필터링 | **서버** (리스트 응답) — 클라 작업 아님 |
| 특정 등급의 액션(댓글·DM 등) 차단 | **서버** (API 에러) + 클라는 기존 에러 처리 — 신규 구현 없음이 기본 |
| 클라 조건문이 진입 자체를 막는 게이트 | **클라** — 4단계에서 지점 확정 |
| 서버 config 플래그로 제어되는 기능 | 서버 값 + 클라 게이트 유지/교체 |

- 이 배정은 초안이며, 4단계 코드 확인으로 "클라 작업 없음"까지 확정합니다.
- 판단이 갈리는 정책(예: 준회원 포함 여부)은 임의 확정하지 말고 **확인 사항 후보**로 적어둡니다.

### 4단계 — 코드베이스 전수조사

1단계 5항에서 확정한 조사 대상(`SWEEP_ROOT` — 앱 레포 또는 사용자가 지정한 경로)에서 실제 코드로 판단을 확정합니다. **조사 메모에는 `파일경로:라인` 을 남기되, 문서에 옮길 때는 핵심 클래스명만 적습니다** (작성 원칙 1). 근거는 리뷰 질문이 나올 때 답할 수 있으면 충분합니다.

1. **게이트/차단 지점 전수 검색** — 대상 화면의 Route/Path 명, 관련 플래그(`canWriteStory` 등), 등급 판별 함수(`isPublicDomain` 등)로 grep:
   ```bash
   grep -rn "canWriteStory\|isPublicDomain\|isFullFledgedMember" --include="*.kt" . | grep -v test
   ```
   진입점이 여러 곳(피드·프로필·딥링크·푸시 수렴점 등)에 흩어져 있음을 전제로, **찾은 것에서 멈추지 말고 호출처를 역추적**합니다. 문서에는 "N곳" 과 대표 클래스명만 남깁니다.
2. **하위 표면 재조사 (게이트 완화 작업일 때 필수)** — 완화되는 게이트가 보호하던 화면 내부의 액션 UI(작성 버튼·메뉴·입력창)를 찾습니다. 해당 액션의 네비게이션 Path(`StoryWritePath` 류)로 **호출처 전수 검색**을 돌려, 게이트 없는 호출을 모두 확인하고 각각 "서버 드리븐인지(작업 불필요) / 클라 하드코딩인지(게이트 추가)"를 판정합니다.
   - 노출 조건이 서버 응답 필드/리스트 아이템 타입에서 오면 서버 드리븐, Composable 에 무조건 렌더링이면 하드코딩.
3. **기존 패턴 확보** — 신설할 파이프라인과 동일한 기존 사례(예: `AppConfig` 의 신설 필드 → `Authenticator` getter → UseCase)를 찾아 참조 클래스명으로 기재합니다. 신설 필드의 default 값과 fail-closed/open 방향을 여기서 결정합니다.
4. **"작업 불필요" 도 코드로 확인** — 좋아요·수정/삭제처럼 "될 것 같은" 항목도 핸들러 원문을 열어 등급 체크 유무·소유권 분기(`isMine` 류)를 확인하고 비목표에 한 줄 근거로 기재합니다.
5. **회귀 포인트 수집** — 같은 플래그를 쓰는 다른 화면(FAB·바텀네비 등)을 확인해 "그대로 둔다"를 해당 Task 의 위험 요소에 명시합니다.

### 5단계 — 교차검증 (타 플랫폼 스펙 제공 시)

2단계에서 뽑은 항목 ①~⑤를 Android 조사 결과와 대조합니다. 대조는 **Android 작업 판단을 확정하기 위한 절차**이므로, 대조표를 문서에 옮기거나 독립 섹션을 만들지 않습니다 — 아래 기준으로만 반영합니다.

| 결과 | 문서 반영 |
|---|---|
| 일치 | 따로 적지 않는다 — Android 판단이 달라지지 않는다 |
| 스펙 기준으로 Android 를 맞춤 | 해당 Task 설명 안에 "왜 이 기준인지" 한 문장 |
| 판단이 필요한 충돌(UX 방식 등) | 확인 사항으로 승격 |
| 플랫폼 구조 차이(진입점 수 등) | 충돌이 아니라 배경 — 필요하면 Task 설명에 한 줄, 일정 산정에 반영 |

### 6단계 — 문서 작성

`<티켓키>-planning.md` 를 1단계 5항에서 확정한 위치(`DOC_DIR` — 기본은 앱 레포 루트)에 생성합니다. 아래 **문서 템플릿 전문**을 사용하고, `SKILL.md` 의 작성 원칙 12개를 적용합니다.

**Task 구조** — 문서를 쓰기 전에 4단계 조사 결과로 Task 경계를 먼저 정합니다(기준은 `SKILL.md` "Task 구조"). 작업이 하나여도 `전체 Task 요약` + `Task 1` 형태를 유지합니다.

**분량 기준 (피드백 반영)** — 이 문서는 방향을 잡는 문서입니다:

- Task 설명은 **맥락 위주**로 씁니다. "왜 이 구조를 골랐는지 / 무엇이 바뀌는지 / 어디가 까다로운지" 순으로 서술하고, 구현 순서·세부 분기는 적지 않습니다.
- **문제 정의·Task 설명은 줄글이 아니라 "요약 한 줄 + 하위 들여쓰기 bullet" 구조로** 씁니다 (`SKILL.md` §본문 서술 구조). 상위 라인에는 고유명사를 두지 않고, 클래스명은 하위 bullet 으로 내립니다.
- **코드 스니펫은 필요한 곳에만** — 기본은 생략입니다. 다만 특이한 구조이거나 코드를 봐야 판단이 서는 Task 는 **몇 줄짜리 스니펫을 붙여도 됩니다**(조건 방향 반전, 기존 계약과 다른 시그니처 등). 길게 붙여넣거나 구현 순서를 코드로 나열하지는 않습니다.
- **파일 경로·라인 번호를 쓰지 않습니다.** 핵심 클래스명만 적습니다 (`WebViewScreen`, `DMRewardBottomSheetState` 처럼). 표의 참조 열도 클래스명까지만.
- **비즈니스 로직이 없는 단순 모델 생성(DTO·Entity·VO·UiState)은 설명하지 않습니다** — 작업 표에 한 줄이면 충분합니다. 변환 규칙·기본값처럼 판단이 들어간 부분만 문장으로 남깁니다.
- **문체는 명사형 종결** — 문서의 모든 문장·표 셀·목록을 "~함 / ~했음 / ~임" 으로 끝냅니다 (작성 원칙 12). 아래 템플릿의 `<…>` 자리표시자를 채울 때도 같은 문체로 씁니다.

**섹션별 작성 요령**:

| 섹션 | 요령 |
|---|---|
| 문제 정의 | **기획 개요 → 이번 작업의 방향 → 현재 동작 → 문제** 순으로 요약+하위 bullet + 정책↔구현 주체 표. 기획 개요는 최소 맥락만, 방향은 한 줄 결론만 |
| 비목표 | `# 비목표` 헤딩 + 접기. 항목당 한 줄 — "왜 안 해도 되는가"가 한 줄로 읽히게 |
| API 설계 | 신규 신설인지 기존 확장인지 먼저 결론. 요청·응답은 **표가 아니라 JSON 코드블록**으로 씁니다. **하위호환 기본값 방향**(모르는 값/필드 부재 시 동작)을 반드시 포함하고, 서버와 미확정이면 "안" 임을 명시하고 확인 사항으로 |
| 전체 Task 요약 | Task · 내용 요약 · 의존 3열. **일정 열 금지.** 표 아래에 Task 경계를 어떻게 잘랐는지 1~2문장 |
| Task N | **Task 개요** → **작업 범위**(맥락 위주) → **개발 방향**(갈렸던 지점·기각한 대안은 여기 하위 bullet) → 작업 표(구성·역할·참조 클래스) → 위험 요소 접기 |
| 위험 요소 | 각 Task 안에 `## 위험 요소` 헤딩 + 접기로. 하위호환·배포 순서·회귀 포인트·치환 실수 지점 중 **그 Task 에 해당하는 것만** |
| 확인 사항 | `# 확인 사항` 헤딩 + 접기. 서버/웹/디자인을 소제목으로 나눈 체크리스트 |
| 테스트 계획 | `# 테스트 계획` 헤딩 + 접기. 회귀·하위호환 행 필수 |
| 예상 일정 | 표 없이 총계 한 줄 + 무엇이 크리티컬 패스인지 1~2문장. Task별 공수 분해 금지 |
| 그 외 섹션 | 표준 양식에 없는 섹션은 임의로 넣지 않는다 — 필요해 보이면 `AskUserQuestion` 으로 묻고 동의를 받은 뒤 추가 (`SKILL.md` 작성 원칙 10) |

### 7단계 — 사용자 검토

- 문서 경로와 핵심 요약(Task 구성 / 클라 작업 N건 / 작업 없음 N건 / 확인 사항 N건)을 보고합니다.
- 피드백을 반영해 문서를 갱신합니다. 판단이 갈리는 지점은 `AskUserQuestion` 으로 확인합니다.
- **문서 승인 전 구현 코드를 작성하지 않습니다.** 승인 후 작업 시작은 `start-work` skill 로 이어집니다 (문서에는 적지 않습니다).

### 8단계 — (옵션) Jira 본문 업로드 제안

문서가 확정되면(7단계 피드백 반영 완료) 마지막으로 **Jira 이슈 본문 업로드 여부**를 묻습니다.

- `AskUserQuestion` 으로 "플래닝 문서를 Jira 이슈(<티켓키>) 본문에 업로드할까요?"를 질문합니다.
- **사용자가 동의할 때만** `update-jira-description` skill 을 Skill 도구로 호출합니다 (인자: 문서 경로). 티켓 키 확인 등 이후 절차는 해당 skill 이 담당합니다.
- 문서의 접기 마커(`<details>`)는 그 skill 이 접기 변환을 지원할 때 **Jira 접기(ADF expand)로 변환**됩니다 — 변환 여부는 그 skill 이 묻습니다.
  지원하지 않는 버전이면 마커가 원문 그대로 올라가므로 그 사실만 사용자에게 알립니다. **어느 경우든 여기서 마커를 미리 풀거나 지우지 마십시오.**
- **자동 진행 금지** — 기존 Jira 본문을 덮어쓰는 동작이므로 반드시 동의 후 실행하고, 거절하면 그대로 종료합니다.

## 품질 기준

- [ ] 클라 작업/비목표의 모든 판단이 **실제 코드 확인**에 근거한다 (문서 표기는 클래스명까지)
- [ ] 문서에 **파일 경로·라인 번호가 없다** — 고유명사는 클래스명 수준
- [ ] 정책 ↔ 구현 주체 표에서 서버/클라 책임이 한눈에 갈린다 (범위 부풀리기 없음)
- [ ] API 설계 섹션이 요청·응답을 **JSON 코드블록**으로 담고 있고 **하위호환 기본값 방향**이 있다 (API 변경이 있는 경우)
- [ ] 전체 Task 요약 표가 있고 **일정 열이 없으며**, Task 간 의존·순서가 적혀 있다
- [ ] Task 설명이 맥락 위주다 — 코드 스니펫은 판단에 필요한 지점에만 짧게, 단순 모델 생성 설명 없음
- [ ] 문제 정의·Task 설명이 **요약 한 줄 + 하위 들여쓰기 bullet** 구조다 (줄글 나열 아님), 상위 라인에 고유명사가 없다
- [ ] 위험 요소가 **각 Task 안에 접기로** 들어가 있다 (독립 섹션 없음)
- [ ] 비목표·위험 요소·확인 사항·테스트 계획이 **헤딩 + 접기 마커** 조합이고, 마커 앞뒤에 빈 줄이 있다
- [ ] 게이트 완화 작업이면 하위 표면(내부 액션 UI) 전수 재조사 결과가 문서에 있다
- [ ] 타 플랫폼 스펙이 있으면 교차검증에서 나온 충돌·확인 필요 항목이 반영돼 있다 (대조표·독립 섹션 없음)
- [ ] 테스트 계획에 회귀·하위호환 행이 있다
- [ ] 예상 일정이 **표 없이 총계 한 줄** 이다
- [ ] 표준 양식에 없는 섹션을 임의로 넣지 않았다 (필요했다면 사용자에게 묻고 동의를 받았다)
- [ ] 섹션 첫 문장이 고유명사 없이 읽히고, 3개 이상 나열은 표로 정리돼 있다
- [ ] 문서 전체가 명사형 종결(~함/~했음/~임)로 쓰였다 — "~합니다" 체 잔존 없음

## 주의사항

- **문서 승인 전 구현 금지** — 이 스킬의 산출물은 문서까지입니다.
- **커밋·push 금지** — 문서 파일 생성/수정만 하고, 커밋은 사용자가 별도로 지시할 때만 합니다.
- **외부 쓰기는 8단계의 Jira 업로드가 유일**하며, 그마저도 `AskUserQuestion` 동의 후에만 수행합니다. 그 외 Jira/Confluence/GitHub 은 읽기 전용으로만 접근합니다.
- 조사 중 빌드가 필요한 상황은 없습니다 — grep/Read 로만 조사하고, 빌드·테스트 실행은 하지 않습니다.
- **조사를 줄이라는 뜻이 아닙니다** — 전수조사 강도는 그대로 유지하고, 줄이는 것은 문서에 옮기는 분량입니다.
- 위 조사 요령·품질 기준은 **예시이자 하한선**이지 닫힌 목록이 아닙니다 — 티켓 성격에 따라 필요한 조사를 추가하세요.
