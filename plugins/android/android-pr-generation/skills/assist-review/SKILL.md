# Teamblind Android — 리뷰어 보조 (assist-review)

`/assist-review <PR번호>` 로 직접 호출하거나 "이 PR 같이 봐줘" 류 요청 시 발동되는 스킬입니다. **남의 PR**을 논리 단위로 쪼개 격리 워크트리에 마커를 심고 **읽는 순서**를 알려준 뒤 물러납니다. 실제로 코드를 읽고 판단하는 것은 사용자이고, AI 는 그 판단을 **사용자 이름으로 나가는 인라인 코멘트**가 되도록 실어 나릅니다.

> 단계별 상세 실행 절차(정확한 `gh`/`git worktree` 명령과 재개·게시·정리 로직)는 [references/workflow.md](references/workflow.md) 를 참조하세요. 이 문서는 **컨셉·AI 발화 경계·마커 포맷·진행 방식·게시 규칙의 단일 출처(canonical)** 입니다.

> **사전 조건**: GitHub CLI(`gh`)가 설치·인증되어 있어야 합니다.

---

## 컨셉 — 주체는 사람, AI는 지원자

**코드리뷰의 주체는 사람이고, AI는 이해를 돕는 지원자입니다.**

- **AI의 역할 = 이해 가속기.** 남의 코드를 빨리·정확히 파악하게 만듭니다.
- **사람의 역할 = 판정자.** 무엇을 지적할지, 지적할지 말지를 정합니다.

이 축을 택한 이유는 두 가지입니다.

1. **리뷰어로서의 책임** — AI 판정을 그대로 옮겨 적으면, 코드를 이해하지 못한 채 승인하게 됩니다. 리뷰 코멘트는 리뷰어 본인의 이름으로 나갑니다.
2. **코드 파악 속도** — 남의 코드는 맥락을 잡는 데 시간이 오래 걸립니다. AI가 당겨줄 수 있는 건 정확히 그 부분입니다.

### 형제 스킬 `review-pr` 과의 선택 기준

| | `review-pr` | `assist-review` |
|---|---|---|
| 주체 | AI 가 판정 | 사용자가 판정 |
| 산출물 | 8관점 채점 리포트(로컬) | 사용자의 인라인 코멘트(PR 게시) |
| 쓰는 때 | 빠른 훑기, 대형 PR 1차 스크리닝 | 리뷰어로 **책임지고** 봐야 할 때 |

두 스킬은 형제로 공존합니다. **AI가 대신 채점해주길 원하는 요청이면 이 스킬이 아니라 `review-pr` 로 넘깁니다.**

### 라이프사이클의 핵심 — 마커는 워크트리와 함께 죽는다

마커는 원본 리포가 아니라 `~/claude-review/<repo>/pr-<N>/` 격리 워크트리에만 존재합니다. 리뷰가 끝나면 워크트리를 통째로 제거하므로 **마커를 "지우는" 별도 단계가 없습니다** — 지울 걸 잊는 실패 모드 자체를 제거한 구조입니다.

워크트리의 HEAD 는 **PR head** 입니다. 따라서 `git diff` 에 잡히는 것은 **AI가 심은 마커·경계 주석과 사용자가 쓴 코멘트뿐**이고, 이 성질이 두 가지를 동시에 해결합니다.

- IDE 의 변경 내비게이션(다음/이전 변경)이 **마커 사이를 건너뛰는 단축키**가 됩니다.
- 수확이 단순해집니다 — diff 에서 AI 삽입분만 빼면 남는 게 사용자의 코멘트입니다.

**남의 브랜치를 로컬에서 만지는 것이므로 커밋·푸시는 어떤 경우에도 하지 않습니다.**

## AI 발화 경계

이 스킬의 존재 이유입니다. 아래 네 조항은 어떤 상황에서도 완화하지 않습니다.

- **판정 서술 금지** — "이건 버그다 / 고쳐야 한다 / P0 다 / 컨벤션 위반이다" 라고 쓰지 않습니다. 우려는 반드시 **물음표로 끝나는 열린 질문**으로 변환합니다.
- **점수·등급 없음** — `review-pr` 의 8관점 채점과 P0/P1/P2 우선순위는 이 스킬에 존재하지 않습니다.
- **코멘트를 AI 가 만들어내지 않습니다** — 게시되는 것은 사용자가 워크트리에 쓴 주석과 채팅으로 말한 것뿐입니다. 문장을 다듬을 수는 있어도 **없는 판단을 지어내지 않습니다.**
- **깊이의 결정권도 사용자에게** — `더 설명` 을 요청하지 않으면 그 단위를 더 파고들지 않습니다.

### 우려 → 질문 변환

우려가 떠오르는 것 자체는 정상입니다. 그걸 **어떤 형태로 내보내느냐**가 이 스킬의 규칙입니다.

| 떠오른 우려 | ❌ 판정 서술 | ✅ 열린 질문 |
|---|---|---|
| 스크롤 복원 key 가 id 뿐 | "id 만 보면 버그다" | "목록만 갱신되고 id 가 같은 경우엔 어떤 동작을 의도한 건가요?" |
| UseCase 에 스코프가 붙음 | "컨벤션 위반이다" | "이 UseCase 가 스코프를 갖는데 의도한 건가요?" |
| 테스트가 없음 | "테스트를 추가해야 한다" | "이 분기는 어떤 경로로 검증되고 있나요?" |
| 상수 의미가 바뀜 | "호출부를 다 고쳐야 한다" | "이 상수를 참조하는 다른 호출부도 같은 의미로 읽고 있나요?" |
| 에러를 무음 catch | "무음 catch 는 금지다" | "이 경로에서 실패가 나면 사용자에겐 어떻게 보이나요?" |

### 프로젝트 컨벤션(SSOT) 사용 방침

`android-arch-patterns` · `android-code-quality` · `android-data-models` 는 **`[확인 필요]` 질문을 만드는 재료로만** 씁니다.

컨벤션과 어긋나 보여도 "위반입니다" 로 쓰지 않고 "의도한 건가요?" 로 변환합니다. 컨벤션을 아는 것은 **더 좋은 질문을 던지기 위한 것**이지, 판정하기 위한 것이 아닙니다.

## 워크트리에 심는 것 두 가지

AI 는 워크트리에 **경계 주석**과 **마커** 두 종류를 심습니다. 역할이 다릅니다.

| | 경계 주석 | 마커 |
|---|---|---|
| 무엇을 표시 | 이 PR 이 바꾼 줄의 **범위** | 논리 단위의 **의도와 질문** |
| 개수 | diff 의 hunk 수만큼 | 논리 단위 수(m) + 참조 지점 |
| 왜 필요 | 인라인 코멘트를 붙일 수 있는 줄이 어디까지인지 | 무엇을 어떤 순서로 볼지 |

### PR 변경 구간 경계 주석

```kotlin
/** ▼──────────────────── PR 변경 시작 ────────────────────▼ */
val searchBarPlaceholder = viewModel.searchBarPlaceholderOverride
    ?: stringResource(id = com.teamblind.feature.home.R.string.home_search_placeholder)
/** ▲───────────────────── PR 변경 끝 ─────────────────────▲ */
```

- **경계 안쪽이 이 PR 의 변경 라인**이고, 곧 **인라인 코멘트를 붙일 수 있는 줄**입니다. GitHub 은 diff 밖 라인에 인라인 코멘트를 받지 않으므로, 이 표시가 잘못된 위치에 코멘트를 남기는 것을 막습니다.
- IDE 의 변경 표시(거터)에 의존하지 않습니다. **워크트리는 IDE 가 Git 루트로 인식하지 못하거나 거터가 뜨지 않는 경우가 있어**, 정보를 코드 안에 텍스트로 박아두는 편이 확실합니다.
- `/** */` 를 쓰는 이유는 Kotlin 렉서가 이를 **KDoc 토큰**으로 잡아 줄 주석과 색 슬롯이 분리되기 때문입니다. `Settings → Editor → Color Scheme → Kotlin → KDoc comment` 에서 이것만 색을 올리면 일반 주석·마커 색은 그대로 둔 채 경계만 눈에 띕니다.
- 순수 삭제 지점은 감쌀 줄이 없으므로 한 줄로 표시합니다: `/** ◆──── 이 지점에서 삭제됨 ────◆ */`
- 경계 주석은 **수확 대상이 아닙니다.** 마커와 함께 diff 에서 제외합니다.

> **분량 주의**: 경계는 hunk 당 2줄입니다. hunk 가 잘게 흩어진 PR 에서는 코드보다 경계가 많아질 수 있으므로, **3줄 이내로 붙어 있는 hunk 는 하나로 병합**해 감쌉니다.

### 대표 마커 (단위당 1개)

```kotlin
// TODO(review 1/6 (1)): 캐러셀 State 를 별도 컴포저블로 분리
//  [변경사항 요약] ViewModel 이 id 별 최신 UiState 를 보관하고 Flow 로 내려주도록 바꿈
//  [확인 필요] id 는 같은데 아이템 목록만 바뀌면 스크롤이 안 돌아가나?
//  [확인 필요] 회전 후 복원 경로에서도 이 분기를 타나?
```

- **`TODO` 접두는 필수입니다.** Android Studio TODO 패널은 기본적으로 `TODO` 키워드만 잡습니다.
- `[변경사항 요약]` — 이 단위에서 **무엇이 어떻게 달라졌는지**. 호출 경로 나열이 아닙니다.
- `[확인 필요]` — **반드시 물음표로 끝나는 열린 질문.** 0개도 허용합니다(질문거리가 없으면 억지로 만들지 않습니다).
- 마커는 그 단위의 **경계 주석 바로 위**에, 같은 들여쓰기로 넣습니다.
- **마커에 사용자가 채울 칸을 두지 않습니다.** 코멘트는 사용자가 원하는 줄 위에 직접 씁니다.

### 참조 마커 (한 줄)

한 단위가 여러 파일에 걸칠 때, 대표 지점 **외의** 지점에 붙입니다.

```kotlin
// TODO(review 2/6 (2)): 되돌리기 판단용 비교 키 추가 — 본문 State.kt:81
```

- **한 단위가 여러 파일에 걸칠 때만 `(k)` 순번을 붙입니다.** k 는 **읽는 순서**이고 대표가 항상 `(1)` 입니다. 번호 하나로 "본문이 어느 것인지"와 "무엇을 먼저 볼지"가 동시에 해결됩니다.
- **단일 파일 단위는 순번 없이** `TODO(review 3/6)` 입니다.
- `— 본문 <파일>:<라인>` 으로 대표 위치를 명시합니다. 같은 파일명이 여러 모듈에 있으면(`build.gradle.kts` 등) 모듈 경로까지 적습니다.
- 한 줄 텍스트는 **그 파일이 이 변경에서 맡은 역할**을 말합니다.

### 배치 예시

```
Contract.kt:24    → TODO(review 2/6 (2)): 되돌리기 판단용 비교 키 추가 — 본문 State.kt:81
State.kt:81       → TODO(review 2/6 (1)): 콘텐츠가 바뀐 경우에만 첫 아이템으로 되돌리기
                     [변경사항 요약] / [확인 필요]
ViewModel.kt:108  → TODO(review 2/6 (3)): 비교 키를 채워 내려보내는 쪽 — 본문 State.kt:81
```

**TODO 패널은 파일 알파벳순이라 `(1)` 이 맨 위에 오지 않습니다.** 위 예시도 패널에서는 `Contract.kt (2)` 가 먼저 뜹니다. 그래서 순번이 필요합니다.

### 파일 타입별 주석 문법

| 확장자 | 마커 | 경계 |
|---|---|---|
| `.kt` `.java` `.kts` `.gradle` | `//` | `/** */` |
| `.xml` | `<!-- -->` | `<!-- -->` |
| `.properties` `.yml` `.yaml` `.toml` `.cfg` | `#` | `#` |
| `.json` · 바이너리 · 생성물 | **불가** — [채팅 전용 단위](#채팅-전용-단위-마커-불가-파일) | 불가 |

**한 파일에 여러 마커는 정상입니다** — 분할 기준이 파일이 아니라 의도이기 때문입니다.

> TODO 패널에는 **정렬 옵션이 없습니다.** 그룹화(모듈·패키지)만 있고 파일은 경로 알파벳순, 파일 안에서는 라인순으로 고정입니다. 그래서 `(n/m)` 과 `(k)` 를 마커 제목에 박아둡니다 — 순서는 마커 번호와 채팅의 지도로 따라갑니다.

## 논리 단위 분할

- 파일 순서가 아니라 **변경의 의도** 단위로 자릅니다.
- 커밋이 이미 의도 단위로 쪼개져 있으면 **커밋을 1차 후보**로 씁니다. 커밋이 지저분하면 재구성합니다.
- 순서는 **진입점 → 안쪽**. 사용자 눈에 보이는 변화(Composable/화면)를 먼저 놓고, 그걸 뒷받침하는 ViewModel · UseCase · Repository 순으로 들어갑니다. 남의 코드는 "이게 화면에서 뭐가 달라지는 건데?" 가 먼저 잡혀야 나머지가 붙습니다.

### 상한 — m ≤ 20

먼저 **유사·인접 변경을 한 단위로 합쳐** 20 이하로 맞춥니다. 그래도 넘으면 진행 전에 사용자에게 묻습니다(`AskUserQuestion`).

| 선택지 | 동작 |
|---|---|
| 전체 진행 | m 을 그대로 두고 전부 마커·지도에 올림 |
| 핵심 20개만 | 상위 20개만 마커·지도 대상으로 하고, 나머지는 "그 외 변경" 요약 1개로 채팅에만 알림 |
| 범위 좁히기 | 사용자가 지정한 경로/모듈만 대상으로 다시 분할 |

**범위를 줄이는 결정도 사용자 몫입니다.** AI가 임의로 잘라내고 "중요한 것만 봤다" 고 하지 않습니다.

### 채팅 전용 단위 (마커 불가 파일)

JSON·바이너리·생성 파일처럼 주석을 넣을 수 없는 변경도 **단위에서 빼지 않습니다.** 마커만 생략하고 지도에는 `[마커 없음]` 으로 등장시키며, 심을 곳이 없는 `[변경사항 요약]`·`[확인 필요]` 는 지도 아래에 채팅으로 함께 적습니다. 코멘트는 `지적 <n>` 으로 받습니다.

## 진행 방식 — 지도를 주고 물러난다

**AI 는 지도를 한 번 출력하고 물러납니다.** 코드를 읽는 주체는 사용자이고, 속도와 순서의 결정권도 사용자에게 있습니다.

마커 안에 `[변경사항 요약]` 과 `[확인 필요]` 가 이미 들어 있으므로, **같은 내용을 채팅에서 한 단위씩 다시 읽어주지 않습니다.** 채팅이 기여하는 것은 세 가지뿐입니다 — TODO 패널이 못 하는 **순서 안내**, 요청받았을 때의 **더 설명**, 그리고 **마무리 수확·게시**.

### 지도 — 읽는 순서


- **`코멘트 남기는 법` 블록은 지도를 출력할 때마다 함께 냅니다.** 이 스킬을 처음 쓰는 사람은 마커만 보고는 자기가 무엇을 해야 하는지 알 수 없고, 재개 시에도 잊었을 수 있습니다. 짧으므로 매번 내는 비용보다 빠뜨렸을 때의 손실이 큽니다.
- 지도를 출력한 뒤에는 **먼저 말을 걸지 않습니다.** 진행 상황을 캐묻거나 다음 단위로 밀지 않습니다.

### 사용자 명령

| 입력 | 동작 |
|---|---|
| `더 설명 <n>` | n 번 단위만 깊게 (아래 누적 단계) |
| `지적 <n> <내용>` | 그 내용을 n 번 대표 지점 위에 주석 한 줄로 적음(사용자가 직접 쓰는 것과 같은 형태) |
| `마무리` | 수확 → 사용자 확인 → 인라인 코멘트 게시 → 워크트리 제거 |

- 번호를 생략하고 물으면 직전에 다룬 단위로 해석하고, 모호하면 **어느 단위인지 되묻습니다.**
- `지적` 은 편의 기능일 뿐입니다. **IDE 에서 직접 주석을 쓰는 쪽이 기본**입니다.
- 정확히 이 단어가 아니어도 의도가 같으면 같게 처리합니다(예: "3번 더 파봐" → `더 설명 3`, "다 봤어" → `마무리`).

### `더 설명` 의 누적 단계

| 차수 | 다루는 것 |
|---|---|
| 1차 | 호출 경로(누가 부르고 어디로 흘러가나), 이 변경 이전의 구현 |
| 2차 | 관련 테스트, 변경 이력(`git log -S` · `git blame`), 주변 기존 코드와의 관계 |
| 3차 이상 | 미리 정해진 축 없음 — 사용자의 구체 질문에 답합니다 |

> 같은 단위에서 2차까지 갔는데 또 `더 설명` 만 입력하면, **새 내용을 지어내지 말고 무엇이 궁금한지 되묻습니다.**

> 곁길(IDE 설정·마커 형식 논의 등)로 샜다가 돌아왔을 때, 사용자가 위치를 잃었으면 **"대기 중" 이라고 참조하지 말고 지도를 다시 출력합니다.**

## 사용자가 코멘트를 남기는 법

**지적하고 싶은 줄 위에 평범한 주석을 씁니다. 그게 전부입니다.**

```kotlin
// 리소스로 빼는 게 좋겠습니다
"B" -> "검색어를 입력해주세요"

// 3 이 세 줄이 같은 값을 두 번 계산합니다
val a = compute()
val b = compute()
val c = a + b
```

- 특별한 접두어가 **필요 없습니다.** 워크트리의 HEAD 는 PR head 이고 아무것도 커밋하지 않으므로, 사용자가 친 줄은 diff 에 전부 뜨고 PR 작성자가 원래 써둔 주석과 자동으로 갈립니다. AI 가 심은 마커·경계는 고정 패턴이라 제외됩니다.
- 기본 범위는 **바로 아래 한 줄**입니다. 숫자 접두(`// 3 내용`)를 붙이면 아래 3줄이 됩니다.
- **어디에나 쓸 수 있습니다** — 대표 마커 위, 참조 마커 위, 마커가 없는 아무 줄.
- **경계 주석 안쪽에 써야 인라인으로 게시됩니다.** 바깥(문맥 줄)에 쓰면 GitHub 이 받지 않습니다.
- 라인 번호는 수확할 때 diff 의 hunk 정보로 **PR head 기준으로 자동 환산**합니다. 사용자가 셀 일이 없습니다.
- 앵커가 변경 라인 밖이면 **버리지 않고 가장 가까운 변경 라인을 제안**합니다. 범위 안에 변경 라인이 있으면 그쪽으로 좁힙니다.
- 사용자가 주석이 아니라 **코드를 고친 경우**, 그건 코멘트로 취급하지 않고 "코드 수정이 감지됐다" 고만 알립니다. 워크트리는 실험장이 아니라 읽는 곳입니다.

## 마무리 — 수확 · 게시 · 정리

`마무리` 한마디로 세 가지가 순서대로 일어납니다. **마무리 시점은 사용자가 정합니다.** "아직 n 번 단위를 안 보신 것 같은데 계속할까요?" 로 붙잡지 않습니다 — AI 는 사용자가 무엇을 읽었는지 알 수 없고, 알 필요도 없습니다.

### 1. 수확 후 확인받기

수확한 코멘트를 **게시 직전 형태 그대로** 보여주고 확인을 받습니다. 사용자 이름으로 나가는 글이므로 **확인 없이 게시하지 않습니다.**

```
게시할 인라인 코멘트 3건

  feature-home/.../HomeTopBarState.kt:38-39
    스크롤 복원 조건이 id 에만 걸려 있어서 목록만 갱신되는 경우를 못 잡습니다.

  feature-home/.../HomeTopBarViewModel.kt:44
    리소스로 빼는 게 좋겠습니다.

  domain-search/.../SearchDao.kt:16
    네이밍 변경이 필요할 것 같습니다.

인라인 불가 1건
  HomeTopBarState.kt:47-51 — 이 PR 의 변경 라인이 아님. 가장 가까운 변경 라인은 54

게시할까요? (전체 게시 / 일부만 / 게시 안 하고 초안만)
```

- 문장은 다듬되 **내용을 보태지 않습니다.** 사용자가 쓴 것만 나갑니다.
- 인라인 불가 건은 **게시 목록에서 빼고** 따로 보여줍니다.

### 2. 게시

하나의 리뷰(`event: COMMENT`)로 묶어 게시합니다. 상세 명령은 [references/workflow.md](references/workflow.md) 5단계.

- **`APPROVE` · `REQUEST_CHANGES` 는 쓰지 않습니다.** 그건 판정이고, 판정은 사용자가 GitHub 에서 직접 누릅니다.
- 게시 후 리뷰 URL 을 안내합니다.

### 3. 초안과 워크트리 정리

- **게시에 성공하면 초안 파일을 남기지 않습니다.** 게시된 것이 정본이므로 중복 사본을 두지 않습니다.
- **게시하지 않았거나 일부만 게시했다면 초안을 남깁니다.** 남은 것(인라인 불가 건 포함)만 담아 `~/claude-review/<repo>/pr-<N>-draft.md` 에 씁니다 — 워크트리 **밖**이라 정리 후에도 남습니다.
- 워크트리 제거를 **확인받고** 지웁니다. 마커의 수명이 워크트리의 수명에 묶여 있어, 마커를 따로 지우는 단계는 존재하지 않습니다.

### 재개

- 같은 PR 번호로 다시 들어오면 **기존 워크트리를 감지해 지도를 다시 출력합니다.** 마커는 그대로 있으므로 다시 심지 않습니다.
- **진행 상태는 추적하지 않습니다.** 몇 개를 봤는지, 코멘트가 몇 건 쌓였는지 세지 않고 알리지도 않습니다. 읽었지만 지적할 게 없어 아무것도 안 쓴 단위와 아직 안 본 단위는 구분할 방법이 없고, 구분하려 드는 순간 AI 가 진행을 관리하는 구조로 되돌아갑니다.

## 외부 변경 규칙

이 스킬이 바깥에 만드는 변경은 **사용자 확인을 거친 인라인 코멘트 게시 하나뿐**입니다. 아래는 **어떤 경우에도 하지 않습니다.**

- ❌ **git commit / git push** — 워크트리 안이라도 절대 금지. 마커는 커밋 대상이 아닙니다
- ❌ **원본 리포 작업 트리 수정** — 마커도 초안도 원본 경로에 쓰지 않습니다
- ❌ **Approve / Request changes** — PR 상태를 바꾸는 판정은 사용자가 직접 누릅니다
- ❌ **확인 없는 게시** — 수확 목록을 보여주고 승인을 받은 뒤에만 게시합니다
- ❌ **사용자가 쓰지 않은 내용 게시** — AI 가 만들어낸 문장은 나가지 않습니다
- ❌ **PR 용 로컬 브랜치 생성** — 워크트리는 detached HEAD 로 만듭니다(정리 후 잔여 브랜치 0)

## 엣지 케이스 처리

**엣지 케이스는 *분할 방식·분량*만 조정합니다. AI 발화 경계와 게시 확인 절차는 어떤 경우에도 유지합니다.**

| 상황 | 처리 방침 |
|---|---|
| 대형 PR (단위 20개 초과) | 병합 → 그래도 넘으면 사용자에게 3지선다 |
| hunk 가 잘게 흩어진 PR | 3줄 이내로 붙은 hunk 를 병합해 경계 주석 수를 줄임 |
| 변경이 1~2개 파일뿐 | 절차는 그대로. 단위가 1개여도 `(1/1)` 로 진행 |
| PR 설명이 비어 있음 | 지도를 그리기 전에 커밋 메시지·연결 티켓으로 의도를 추정하고, 추정임을 밝힙니다 |
| 리소스/생성물만 바뀐 PR | 전부 채팅 전용 단위가 될 수 있음. 워크트리는 그대로 만들되 마커 0개임을 알립니다 |
| 본인이 작성자인 PR | 이 스킬의 범위(남의 PR) 밖임을 알리고 계속할지 확인합니다 |
| 사용자가 "그냥 판정해줘" 라고 요청 | 이 스킬의 경계를 알리고 `review-pr` 로 넘길지 확인합니다 |
| 사용자가 한동안 말이 없음 | 아무것도 하지 않습니다. 읽는 중이므로 재촉하지 않습니다 |
| 게시 실패 | 초안을 남기고 실패 사유를 그대로 전달합니다. 조용히 넘어가지 않습니다 |
