# Teamblind Android — PR 코드 리뷰

`review-pr <PR번호>` 를 지정해 요청하거나 "이 PR 리뷰해줘" 류 요청 시 자동 발동되는 스킬입니다. GitHub PR을 **8개 관점**(아키텍처·코드 품질·성능·가독성·재사용성·버그가능성·테스트·보안)으로 다차원 분석하고, 실행 가능한 한국어 마크다운 리뷰 리포트를 **로컬 파일로 생성**합니다.

> 단계별 상세 실행 절차(정확한 `gh`/셸 명령과 컨텍스트 격리 로직)는 [references/workflow.md](references/workflow.md) 를 참조하세요. 이 문서는 **리뷰 기준·채점 루브릭·리포트 포맷의 단일 출처(canonical)** 입니다.

> **사전 조건**: GitHub CLI(`gh`)가 설치·인증되어 있어야 합니다.

> ⚠️ **이 스킬은 로컬 리뷰 리포트 파일만 생성합니다.** 커밋·푸시·GitHub PR 리뷰 게시·리퀘스트 체인지 등 외부 변경은 절대 수행하지 않습니다. 상세는 아래 [외부 변경 금지](#외부-변경-금지) 참조.

---

실행 전에 [실행 환경 지침](references/execution-environment.md)을 읽고, 현재 환경에 맞는 도구·질문·스킬 참조 방식을 적용합니다.

## 리뷰 관점 (8개) 과 판정 기준 (SSOT 참조)

리뷰는 아래 **8개 관점**으로 수행합니다. 이 8개 관점은 **채점 항목·리포트 "관점별 리뷰" 섹션과 1:1로 일치**합니다(불일치 금지). **각 관점의 판정 기준 자체는 재서술하지 않고 기존 단일 출처를 따릅니다.** (중복 정의 금지)

| 관점 | 스코프 | 판정 기준의 단일 출처 |
|---|---|---|
| **아키텍처** | Clean Architecture 계층·의존성 방향(UI→Domain→Data)·Hilt DI(스코프/`@Binds`/순환)·패키지 구조·고급 패턴(Behavior/Action/Global Event/DataStore/Multi-Source) | 프로젝트 지침 + `android-arch-patterns` |
| **코드 품질** | SOLID·SRP·DRY·함수 복잡도·네이밍·에러 핸들링(`runSuspendCatching` 등) | `android-code-quality` |
| **성능** | `@Stable`/`@Immutable`·메모리 누수·Coroutines/Flow·불필요 recomposition·Strong Skipping Mode의 `remember` key | `android-code-quality` |
| **가독성** | 명확성·명명의 직관성·제어 흐름 이해 용이성·불필요한 복잡성/주석 | 본 스킬(아래 체크리스트) + `android-code-quality`(네이밍 규칙) |
| **재사용성** | 중복 제거·공통화·모듈화 가능성·데이터 변환 계층 분리(Entity → VO → UiState) | `android-data-models` + `android-code-quality` |
| **버그가능성** | null 안전성(platform type, `!!` 남용)·경계 조건·동시성·예외 흐름·누락된 dispose·여러 파일이 얽힌 상호작용·화면 회전/프로세스 사망 후 상태 복원 등 잠재 결함 | 본 스킬 + `android-code-quality` |
| **테스트** | 커버리지·mockable 구조·테스트 설계 | 본 스킬(아래 체크리스트) + `android-code-quality`(testability 패턴) |
| **보안** | 민감정보(토큰·자격증명·개인정보) 로그/하드코딩/평문 노출·권한·저장 방식 | 본 스킬 (아래 체크리스트) |

> 위 스킬들이 SSOT이므로, 리뷰 중 규칙 충돌이 의심되면 본 문서가 아니라 해당 스킬/프로젝트 지침를 기준으로 판정합니다.

### 체크리스트·스코프는 '예시'이지 '전부'가 아님 (비전수)

본 문서의 모든 관점 스코프·체크리스트는 **검사의 출발점(예시)이지 전체 목록이 아닙니다.** "목록에 없다"는 "검토 불필요"를 뜻하지 않습니다. 각 항목은 *"다음을 포함하되 이에 국한하지 않는다"* 로 읽고, **이 PR 고유의 위험을 목록 밖에서 능동적으로 찾습니다.** 리뷰는 항목을 하나씩 지우는 체크박스 작업이 아니라, 예시를 단서(seed) 삼아 그 너머를 탐색하는 작업입니다.

> 목록 밖 위험을 능동 탐색하는 구체 절차는 `references/workflow.md` 의 **2.5단계(교차 계층 흐름 따라가기 + 완전성 점검)** 를 따릅니다.

### 성능 — Strong Skipping Mode 주의 (보강 · 예시일 뿐)

- 람다 콜백을 불필요하게 `remember` key에 포함하지 않았는지 확인 (Compose Compiler 2.0+ 에서 자동 메모이즈됨)
- `remember` key에는 상태 값만 사용했는지 확인

### 보안 체크리스트 (예시일 뿐)

- 민감정보(토큰·자격증명·개인정보)가 로그/하드코딩/평문으로 노출되지 않는지 (예: API 키·시크릿을 소스/리소스에 상수로 박지 않았는지)
- 저장·전송 시 적절한 보호(암호화/마스킹)가 적용되었는지
- 권한·접근 제어가 우회되지 않는지
- 외부 입력(딥링크·Intent extra·WebView URL·서버 응답)을 검증 없이 신뢰하지 않는지

### 버그가능성 체크리스트 (예시일 뿐)

- null 안전성 처리(platform type, `!!` 남용 여부)
- 예외 처리 패턴(`runSuspendCatching` 등 프로젝트 컨벤션 준수, 무음 catch 금지)
- 경계 조건·동시성·리소스 해제(dispose) 누락 등 잠재 결함

### 가독성 체크리스트 (예시일 뿐)

> 네이밍 컨벤션 자체는 `android-code-quality`(UseCase 행위 중심 네이밍 등)를 따르고, 아래는 그 외 가독성 판단의 출발점입니다.

- 이름이 의도를 드러내는지(약어·모호한 `data`/`temp`/`flag` 남용 없음)
- 제어 흐름이 평이한지(불필요한 중첩·과도한 분기·조기 반환으로 단순화 가능 여부)
- 죽은 코드·주석 처리된 코드·무엇을 하는지 다시 설명하는 군더더기 주석이 없는지(왜를 설명하는 주석은 권장)

### 테스트 체크리스트 (예시일 뿐)

> 테스트 용이성(`Clock`/디스패처 주입 등) 패턴은 `android-code-quality`를 따르고, 아래는 커버리지·구조 판단의 출발점입니다.

- 핵심 비즈니스 로직(UseCase/도메인 변환·분기)에 대한 테스트가 추가/갱신됐는지
- 외부 의존(시간·네트워크·DispatcherProvider)이 주입돼 mock/fake로 대체 가능한 구조인지
- 회귀를 부르는 변경(버그 수정·경계 조건)에 재현 테스트가 동반됐는지

## 채점 루브릭 (8항목 × 5점 → 종합 10점)

**리포트에는 항상 점수를 산정·표기합니다.** 위 8개 관점 각각을 **0~5점**으로 채점하고(8항목, 합계 최대 40점), 이를 **종합 점수 10점 만점**으로 환산합니다. 점수 생략은 허용하지 않습니다(엣지 케이스 포함).

```
종합 점수(10점 만점) = 8항목 점수 합계(최대 40) ÷ 4   (소수 첫째 자리 반올림)
예) 합계 32 → 32 ÷ 4 = 8.0 / 10
```

| 항목 | 배점 |
|---|---|
| 아키텍처 | 0~5 |
| 코드 품질 | 0~5 |
| 성능 | 0~5 |
| 가독성 | 0~5 |
| 재사용성 | 0~5 |
| 버그가능성 | 0~5 |
| 테스트 | 0~5 |
| 보안 | 0~5 |

> 리포트 헤더에는 **종합 점수(`X/10`)** 와 **항목별 점수표(각 `X/5`)** 를 함께 표기합니다.

## 우선순위 정의

| 등급 | 의미 |
|---|---|
| **P0 — Critical** | 머지 전 반드시 수정 (아키텍처 위반, 버그, 보안 결함 등) |
| **P1 — Important** | 다음 스프린트에 처리 권장 |
| **P2 — Nice to have** | 장기 개선 항목 |

> 모든 critical 이슈는 반드시 P0로 표기합니다.

## 리포트 포맷

리포트 파일명: `pr_<PR번호>_code_review.md` — **전체 한국어**로 작성합니다.

````markdown
# PR #<번호> 코드 리뷰 — <PR 제목>

- **작성자**: <author>
- **리뷰일**: <date>
- **종합 점수**: <X>/10

| 관점 | 점수 |
|---|---|
| 아키텍처 | <0~5>/5 |
| 코드 품질 | <0~5>/5 |
| 성능 | <0~5>/5 |
| 가독성 | <0~5>/5 |
| 재사용성 | <0~5>/5 |
| 버그가능성 | <0~5>/5 |
| 테스트 | <0~5>/5 |
| 보안 | <0~5>/5 |

## 요약
<2~4개 단락으로 작성하고 단락 사이는 빈 줄로 분리한다. 한 덩어리 벽글(한 문단에 모두 욱여넣기) 금지. 권장 구성:
1) PR의 목적·범위·규모(파일 수, +/- 라인) 한 단락,
2) 핵심 성과·잘 된 설계 한 단락,
3) 주요 우려·보완점 한 단락(핵심 항목이 2개 이상이면 `- ` 짧은 불릿으로 분리).>

## 관점별 리뷰
<별도 prose 요약 없이, **이슈가 있는 관점만 `###`로 전개**하고 그 아래 finding을 바로 나열한다. finding은 "finding 작성 구조"를 따르고 제목에 [P0]/[P1]/[P2] 태그, 한 관점 안에서 P0 → P1 → P2 순. 이슈 있는 관점 사이에는 `---` 구분선. **발견 이슈가 없는 관점은 섹션을 만들지 말고 마지막에 한 줄로 묶는다**(예: `발견된 이슈 없음: 가독성·재사용성·보안`). 점수는 헤더 점수표로 모두 확인되므로 빈 섹션을 만들지 않는다.>

### 아키텍처

#### [P0] <이슈 제목>
**위치**: `<파일:라인>`

**문제**
- (개념) ...
- (구체) ...

**원인**
...

**해결방법**
- (원칙) ...
- (적용) ...

**스니펫**
\```kotlin
// Current ... // Suggested ...
\```

---

> 이슈 있는 관점만 위처럼 `###`로 전개(관점 사이 `---`). 발견 이슈가 없는 관점은 마지막에 한 줄로 묶는다:
> `발견된 이슈 없음: 코드 품질·가독성·재사용성·테스트·보안` (빈 섹션 금지 — 점수는 헤더 표로 확인)

## 액션 아이템
<개발자가 바로 수행 가능한 구체적·측정 가능한 작업>

## 잘한 점 (Positive Highlights)
<잘 구현된 부분과 베스트 프랙티스>

## 결론
<종합 평가와 권고>
````

> **구조 원칙**: 관점(카테고리)이 기준 축이고, P0/P1/P2는 각 finding의 **태그**입니다. 카테고리별 prose 요약 섹션은 두지 않습니다(점수 근거는 해당 카테고리의 finding과 점수표로 갈음).

### finding 작성 구조

**모든 P0·P1 finding은 4부(문제 → 원인 → 해결방법 → 스니펫)를 갖춥니다** — 문제만 지적하고 개선안을 빼지 않습니다(P2는 권장). 구조 예시는 위 **리포트 포맷**의 finding 템플릿을 따릅니다(중복 게시 생략).

- **분량은 사안에 맞춰 조절합니다(간결 우선).** 단순한 finding은 각 라벨 아래 1~2문장으로 충분합니다. **개념/구체·원칙/적용으로 줄을 나누는 것은 여러 맥락이 얽혀 일반화가 필요한 복잡한 finding에만 권장**이며 강제가 아닙니다.
- **가독성**: 라벨(`**문제**` 등)은 독립된 줄에 두고 바로 아래부터 내용을 적습니다(라벨과 내용을 한 줄에 붙이지 않음).
- **문제 / 원인 / 해결방법**은 한국어 서술, **스니펫**의 코드·주석은 영어 유지. 개선 효과는 **해결방법**에 함께 적고, 파일 경로:라인은 제목이 아니라 **`위치` 줄**에 둔다.
- 서술은 **개념(맥락) → 구체(파일:라인·클래스)** 순을 권장하되, 고유명사는 식별에 꼭 필요할 때만 쓴다(장식용 나열 금지).

## 한국어 작성 규칙

- 모든 설명·분석은 한국어로 작성 (전문 용어는 영문 병기 가능 — 예: 의존성 주입(Dependency Injection))
- 코드와 코드 주석은 영어 유지
- 전문적이고 공손한 어조 사용
- 모호한 비판 금지 — 구체적이고 실행 가능하게. 문제만 지적하지 말고 대안 제시. 잘한 점도 함께 인정

## 외부 변경 금지

이 스킬의 산출물은 **로컬 리뷰 리포트 파일(`pr_<N>_code_review.md`) 하나뿐**입니다. 아래 외부 변경 동작은 **어떤 경우에도 수행하지 않습니다.**

- ❌ **git commit / git push** — 어떤 브랜치에도 커밋·푸시 금지
- ❌ **실제 PR 리뷰 게시** — `gh pr review`, `gh pr comment`, `create_pull_request_review`, 인라인 코멘트 작성 등 GitHub에 리뷰를 등록하는 모든 동작 금지
- ❌ **리퀘스트 체인지(Request changes) / Approve** — PR 상태를 바꾸는 모든 동작 금지
- ❌ 원본 소스 코드 수정 — 리뷰는 분석·제안까지만. 개선안은 리포트의 스니펫으로만 제시

> 정보 수집 단계의 GitHub MCP 사용은 **read-only 조회**(기존 코멘트/리뷰 이력 보강)로 한정됩니다. 쓰기 동작은 위와 같이 전부 금지입니다.

> 사용자가 리뷰 결과를 GitHub에 직접 반영하길 원하면, 생성된 리포트를 바탕으로 **사용자 본인이** 게시하도록 안내합니다(스킬이 대신 게시하지 않음).

> 단, 다른 스킬(`generate-pr-auto` 의 13단계)이 이 리포트 파일을 읽어 사용자 승인 하에 PR 코멘트로 게시하는 것은 **그 스킬의 동작**이며, 본 스킬(`review-pr`)의 동작이 아닙니다. `review-pr` 자체는 위 금지 원칙대로 어떤 경우에도 게시하지 않습니다.

## 엣지 케이스 처리

**엣지 케이스는 *분석의 깊이·분량*만 조정합니다. 산출물의 고정 핵심은 어떤 경우에도 유지합니다.**

- **고정 핵심 (항상 유지)**: 종합 점수(`X/10`)·항목별 점수표(8항목 `X/5`), 최상위 섹션(요약 / 관점별 리뷰[8개 관점] / 액션 아이템 / 잘한 점 / 결론), 각 finding의 P0/P1/P2 태그, 모든 P0·P1 finding의 4부 구조(문제·원인·해결방법·스니펫), 교차 계층 흐름 따라가기·"목록 밖 위험은?" 자문(최소 1회; 깊이만 가변), **SSOT 컨벤션 로드·대조**(references/workflow.md 0.5단계 로드 + 검증 게이트; 설치돼 있으면 핫픽스에도 생략 불가, 깊이만 가변). → 이들은 엣지 케이스를 이유로 생략하지 않습니다.
- **가변 (조정 가능)**: 각 관점의 분석 분량, 어떤 계층을 먼저/깊게 볼지.

| 상황 | 처리 방침 (깊이 조정만) |
|---|---|
| 대형 PR (>1000줄) | 아키텍처 관련 항목 우선. references/workflow.md 의 계층별 staged 분석으로 컨텍스트 관리 |
| 핫픽스 | Critical(P0) 이슈를 우선 검토하되, 점수·섹션·4부 구조 등 고정 핵심은 그대로 산출 |
| 리팩토링 PR | 가독성·재사용성·테스트에 중점 |
| PR 설명 부족 | 깊은 리뷰 전 작성자에게 맥락 확인 요청 |

## 발동 조건

- `review-pr <PR번호>` 명시 요청
- "이 PR 리뷰해줘", "PR 코드 리뷰", "PR 봐줘", "머지 전에 검토" 류 요청
- PR 리뷰 기준·채점·리포트 포맷 관련 질문

## 관련 파일

- 단계별 상세 실행 절차: [references/workflow.md](references/workflow.md)
- 판정 기준 SSOT: 프로젝트 지침, `android-arch-patterns`·`android-code-quality`·`android-data-models` 스킬

> **설치 의존성**: 판정 기준인 `android-arch-patterns`·`android-code-quality`·`android-data-models`와 계층 분류에 쓰는 `generate-pr-auto`를 같은 호스트에서 사용할 수 있어야 합니다. 물리적으로 같은 폴더에 둘 필요는 없으며, 실행 환경의 스킬 참조 절차로 실제 설치 위치를 확인합니다. 기준 스킬이 없을 때의 제한은 workflow 0.5단계를 따릅니다.
