# PR 코드 리뷰 — 상세 실행 절차

`review-pr` 스킬이 따르는 PR 코드 리뷰의 **단계별 실행 절차**입니다. GitHub PR 정보를 수집하고, 변경 파일을 계층별로 나눠 분석한 뒤, 팀 규격의 한국어 마크다운 리뷰 리포트를 생성합니다.

> 채점 루브릭·우선순위(P0/P1/P2)·리포트 포맷·리뷰 항목의 판정 기준은 모두 **`SKILL.md`** 를 단일 출처로 참조합니다. 이 문서는 그 기준을 적용하는 정확한 `gh`/Bash 명령과 컨텍스트 격리 로직만 정의합니다.

---

## 핵심 원칙 — 컨텍스트 격리 (인라인)

이 스킬은 별도 agent 서브프로세스 없이 메인 컨텍스트에서 실행됩니다. 큰 PR의 전체 diff를 한 번에 컨텍스트로 끌어오면 안 되므로, **계층별 staged 분석**(read → analyze → append → discard)으로 격리 효과를 냅니다.

- 전체 diff를 한 번에 (`gh pr diff <N>` 단독) 덤프하지 **않습니다**.
- 변경 파일을 아키텍처 계층으로 그룹화한 뒤, 그룹별로 diff를 읽고 → 분석하고 → 발견사항을 **리포트 파일(디스크)에 즉시 append** 하고 → 원본 diff는 재참조하지 않습니다.
- 누적되는 것은 메인 컨텍스트가 아니라 디스크의 리포트 파일입니다.
- 생성물·락파일·바이너리 리소스는 pathspec `:(exclude)` 로 애초에 제외합니다.
- **규모에 맞춰 조절(속도)**: 소형 PR(소수 파일/대략 <400줄)은 계층을 1~2회 diff로 묶어 읽어 왕복 호출을 줄여도 됩니다. 엄격한 그룹별 staging은 컨텍스트가 넘칠 위험이 있는 대형 PR에 적용합니다.
- **격리는 "읽는 양"을 관리하는 수단일 뿐입니다.** 계층마다 컨텍스트를 버리면 여러 파일이 얽힌 문제가 사각이 되므로, 이 사각은 **2.5단계(교차 계층 흐름 따라가기)** 로 보완합니다. 격리가 단편적 리뷰를 정당화하지 않습니다.

## 워크플로우

### 0단계 — 도구 사전 준비

- `gh`(GitHub CLI)는 Bash로 호출하므로 별도 스키마 로드가 불필요합니다.
- PR 설명이 부족해 작성자에게 맥락 확인이 필요할 수 있으면, `AskUserQuestion` 이 deferred 상태인지 확인하고 필요 시 `ToolSearch(query="select:AskUserQuestion")` 로 로드합니다.
- `gh` 설치·인증 확인:

```bash
gh auth status
```

미설치/미인증이면 사용자에게 안내하고 중단합니다. (PR 정보 수집 불가)

#### 0.5 — 프로젝트 컨벤션(SSOT) 로드 (**필수 · diff 분석 전에 1회**)

8개 관점 판정은 "일반적 베스트 프랙티스"가 아니라 **이 프로젝트의 컨벤션 준수 여부**로 합니다. 따라서 diff를 분석하기 전에 판정 기준 SSOT를 **실제로 본문까지 로드**합니다. (SKILL.md의 매핑 표가 출처를 지정만 할 뿐, 로드는 이 단계에서 강제합니다.)

로드 대상 (총 4개):

1. **3개 형제 스킬의 SKILL.md 본문** — 같은 `.claude/skills/` 에 설치돼 있으므로 `Read` 로 본문을 읽습니다(또는 `Skill` 도구로 호출). 리뷰 실행 cwd가 대상 저장소가 아닐 수 있으니 경로를 추정해 직접 읽는 쪽이 견고합니다.
   - `android-arch-patterns` — 계층·의존성 방향·Hilt DI·고급 패턴(Behavior/Action/Global Event/DataStore/Multi-Source)
   - `android-code-quality` — SOLID/네이밍/`runSuspendCatching`/`@Stable`·Strong Skipping/상태관리/Compose 최적화
   - `android-data-models` — Entity → VO → UiState 변환 계층·모델 타입별 역할·Gson(nullable+기본값)·`@Stable` 규칙
2. **대상 저장소 루트의 `CLAUDE.md`** — 아키텍처/패키지 구조/프로젝트 컨벤션 개요. 같은 저장소 cwd에서 실행하면 자동 로드될 수 있으나, **다른 cwd에서 실행 시 자동 로드되지 않으므로** 명시적으로 `Read` 합니다.

```bash
# 형제 스킬·CLAUDE.md 위치 확인 (대상 저장소 루트를 <REPO> 로)
ls "$HOME"/.claude/skills/{android-arch-patterns,android-code-quality,android-data-models}/SKILL.md 2>/dev/null
ls <REPO>/.claude/skills/{android-arch-patterns,android-code-quality,android-data-models}/SKILL.md 2>/dev/null
ls <REPO>/CLAUDE.md 2>/dev/null
```

- **미설치/부재 시 폴백**: 해당 SSOT가 없으면 그 관점은 본 스킬의 인라인 체크리스트로만 판정하고, **리포트에 "SSOT 미참조" 한계를 명시**합니다(워크플로우는 멈추지 않음). 단, "찾지 않아서 없음"과 "설치돼 있는데 안 읽음"은 다릅니다 — 설치돼 있으면 반드시 읽습니다.

### 1단계 — PR 정보 수집 (가벼운 것 먼저)

전체 diff를 읽기 전에, 메타데이터와 파일 목록(stat)만 먼저 확보합니다.

```bash
# 메타데이터·파일목록·커밋을 한 번에 (왕복 최소화)
gh pr view <N> --json title,body,author,headRefName,baseRefName,files,additions,deletions,changedFiles,commits
gh pr checks <N>
```

- `additions`/`deletions` 합으로 PR 규모를 가늠합니다(>1000줄이면 SKILL.md 엣지 케이스의 "대형 PR" 방침 적용 — 아키텍처 우선).
- CI 상태에 실패가 있으면 리포트 요약에 반영합니다.
- PR 설명(`body`)이 비어 있거나 부실하면, 깊은 리뷰 전 작성자에게 맥락을 확인할지 판단합니다.

**(선택) 기존 리뷰 코멘트·리뷰 이력 보강 — GitHub MCP**

이미 달린 리뷰 코멘트/승인 이력을 가져와 **중복 지적을 피하고 미해결 코멘트를 리포트에 반영**합니다. 작은 payload라 컨텍스트 부담이 없습니다.

```
mcp__github__get_pull_request_comments(owner=<owner>, repo=<repo>, pullNumber=<N>)
mcp__github__get_pull_request_reviews(owner=<owner>, repo=<repo>, pullNumber=<N>)
```

- 이 도구들은 deferred 상태이므로 호출 전 `ToolSearch(query="select:mcp__github__get_pull_request_comments,mcp__github__get_pull_request_reviews")` 로 스키마를 로드합니다.
- `owner`/`repo`/`<N>` 은 `gh repo view --json owner,name` 또는 현재 리뷰 대상 PR 정보에서 가져옵니다.
- **활용**: 기존 코멘트에서 이미 지적된 항목은 리포트에서 중복 작성하지 않고, 미해결(unresolved) 코멘트는 액션 아이템/우선순위에 반영합니다.
- **MCP 미가용 시 생략**: 헤드리스/cron 등에서 GitHub MCP 서버가 없으면 이 보강 단계는 건너뛰고 `gh` 기반 정보만으로 리뷰를 진행합니다(워크플로우는 멈추지 않음). diff 분석 경로는 항상 `gh` 를 사용합니다.

### 2단계 — 계층별 staged 분석 (컨텍스트 격리 핵심)

1단계의 파일 목록을 아래 아키텍처 계층으로 그룹화합니다 (`generate-pr-auto` 의 **변경 파일 분류 기준**과 동일 — 아래 prefix 목록만으로 자족적이므로 `generate-pr-auto` 미설치 시에도 이 목록을 그대로 적용하면 됩니다):

- **Domain**: `domain-*`, `domain/*`
- **Data**: `data-*`, `data/*`
- **Feature/UI**: `feature-*`, `ui/*`
- **Core/Common**: `core/*`, `shared/*`, `blind-common*`, `test-common`
- **US Market**: `blind-us/*`
- **Resources**: `*/res/*`, drawable/strings/colors/layouts 등

그룹별로 다음을 반복합니다 (한 그룹씩 — 전체를 한 번에 읽지 않음):

```bash
# 해당 계층 파일만 diff 로 읽기 (생성물/락파일/바이너리 제외)
gh pr diff <N> -- <그룹 내 경로...> ':(exclude)**/build/**' ':(exclude)*.lock'
```

- 읽은 그룹을 SKILL.md 의 **리뷰 항목과 판정 기준**에 따라 분석합니다.
- 분석 결과(발견사항·점수 근거·코드 제안)를 즉시 리포트 파일에 append 합니다.
- 다음 그룹으로 넘어가면 이전 그룹의 원본 diff 라인은 재참조하지 않습니다.

> **대형 PR**: 아키텍처에 영향이 큰 계층(Domain → Data → Feature 순)을 먼저 분석하고, Resources 등 영향이 낮은 계층은 요약 위주로 처리합니다.

### 2.5단계 — 교차 계층 흐름 따라가기 + 완전성 점검 (단편화 방지)

2단계의 계층별 staged 분석은 "한 파일/계층 내부" 결함에 강하지만, 계층마다 컨텍스트를 버리는 구조라 **여러 파일이 얽혀 생기는 문제나 이 PR 고유의 위험**을 놓치기 쉽습니다. 2단계 누적 발견을 바탕으로 **최소 1회**, 목록을 지우는 방식이 아니라 흐름을 따라가며 능동적으로 탐색합니다.

- **흐름 따라가기**: 대표 사용자 액션/데이터 1~2개를 골라 계층 끝까지(UI → ViewModel → UseCase → Repository, 또는 상태 홀더·Effect 간) 따라가며, 계층 경계에서의 계약 불일치·중복 호출·누락된 전달이 없는지 본다.
- **완전성 반사 (필수)**: *"이 PR 고유의 위험 중 SKILL.md 의 어떤 관점/체크리스트에도 없는 것은 무엇인가?"* 를 한 번 이상 명시적으로 자문하고, 떠오른 것을 검증한다. (체크리스트는 단서일 뿐 상한이 아니다 — SKILL.md 의 **'비전수' 원칙**)
- 위 두 항목 **자체도 고정 목록이 아니라 탐색을 여는 예시**입니다. PR 성격에 따라 다른 흐름·축(예: 생명주기·동시성·구성 변경)을 스스로 발굴합니다.

> 여기서 나온 결함은 **별도 섹션을 만들지 않고** 기존 8개 관점(주로 버그가능성·아키텍처)에 귀속시켜 4부 구조로 작성합니다. (관점↔점수↔섹션 1:1 매핑 유지)

### 3단계 — 다차원 판정 (8개 관점)

2~2.5단계 발견을 **SKILL.md 의 8개 관점**(아키텍처·코드품질·성능·가독성·재사용성·버그가능성·테스트·보안)으로 판정합니다. 각 관점의 스코프·판정 기준은 SKILL.md 표가 지정한 SSOT(CLAUDE.md / `android-arch-patterns` / `android-code-quality` / `android-data-models`)를 따릅니다 — 여기 재서술하지 않습니다.

- **finding 분류**: 각 이슈를 8개 관점 중 하나에 귀속시키고 제목에 P0/P1/P2 태그, 한 관점 안에서 P0 → P1 → P2 순(별도 prose 요약 섹션 없음).
- **점수**: 8개 관점 각 0~5점 → 합계(≤40) ÷ 4 = 종합 점수(10점). 헤더에 종합 점수 + 항목별 점수표 표기. 작성 형식은 SKILL.md 의 **리포트 포맷·finding 작성 구조**를 따른다.

### 4단계 — 리포트 자동 저장·마무리

리뷰 완료 후 `pr_<N>_code_review.md` 를 **SKILL.md 의 리포트 포맷대로** 작성해 **사용자 확인 없이 자동 저장**합니다(전체 한국어; 로컬 파일이라 외부 영향 없음). 섹션 순서·점수표·관점별 전개/묶음·finding 4부 구조는 모두 SKILL.md 를 따르며 여기서 재서술하지 않습니다.

- 리뷰일은 시스템 컨텍스트의 현재 날짜를 사용합니다.
- 저장 후 파일 경로를 사용자에게 안내합니다. (커밋·푸시·PR 게시는 하지 않음)

> **주의**: 2단계 staged 분석은 계층별 본문을 append 하는 흐름이라, 모든 계층 분석이 끝나야 산정 가능한 **종합 섹션(종합 점수·항목별 점수표·요약·잘한 점·액션 아이템)** 이 누락되기 쉽습니다. 4단계에서 이 종합 섹션을 반드시 채운 뒤, 아래 자체 검증을 통과해야 파일을 확정합니다.

**출력 자체 검증 체크리스트 (파일 확정 전 반드시 수행)**

아래를 모두 통과하지 못하면 누락분을 채운 뒤 다시 점검합니다. 하나라도 빠진 채로 리포트를 확정하지 않습니다.

1. **점수 표기**: 헤더에 종합 점수(`X/10`)와 **8항목 점수표(각 `X/5`)** 가 모두 채워졌는가. 종합 점수가 `합계 ÷ 4` 와 일치하는가. (생략 불가)
2. **섹션·점수 커버리지**: 헤더 / 요약 / 관점별 리뷰 / 액션 아이템 / 잘한 점 / 결론이 존재하는가. **점수표에 8항목이 모두** 있고, 이슈 있는 관점은 `###`로 전개·이슈 없는 관점은 한 줄로 묶여 8개 관점이 빠짐없이 반영됐는가. (빈 섹션 금지)
3. **4부 구조 첨부**: 모든 **P0·P1 finding**에 **문제 → 원인 → 해결방법 → 스니펫** 4부가 갖춰졌는가(문제만 지적하고 해결방법·스니펫을 누락하지 않았는지). 분량은 간결해도 되나 4부는 빠지지 않는다.
4. **가독성 포맷**: 요약이 단락(2~4개)으로 분리됐는가(벽글 금지). finding 라벨(`**문제**` 등)이 독립 줄에 있는가. 이슈 있는 관점 사이에 `---` 구분선이 있는가.
5. **critical=P0 표기**: critical 이슈가 모두 P0로 분류되었는가.
6. **고정 핵심 유지**: 엣지 케이스(핫픽스·대형 PR 등)를 이유로 점수·섹션·4부 구조 등 고정 핵심을 생략하지 않았는가. (엣지 케이스는 분석 깊이만 조정)
7. **외부 변경 0건**: 리뷰 과정에서 commit·push·`gh pr review`·`gh pr comment`·리퀘스트 체인지 등 외부 변경을 일절 수행하지 않았는가.
8. **통합·완전성 점검**: 2.5단계의 교차 계층 흐름 따라가기와 *"목록 밖 위험은?"* 완전성 반사를 최소 1회 수행했고, 그 결과(상호작용/고유 위험 발견 또는 "탐색했으나 추가 없음" 근거)가 리포트에 반영됐는가. 단편 지적 모음으로 끝나지 않았는가.
9. **컨벤션 대조(SSOT) 게이트** *(미충족 시 파일 확정 불가)*: 0.5단계에서 로드한 SSOT 본문을 실제로 **대조**했는가 —
   - **아키텍처** 판정이 `android-arch-patterns` + `CLAUDE.md`(계층/의존성 방향/Hilt/고급 패턴/패키지 구조)와,
   - **코드 품질·성능·가독성·테스트** 판정이 `android-code-quality`(네이밍/`runSuspendCatching`/`@Stable`·Strong Skipping 등)와,
   - **재사용성**(데이터 변환 계층) 판정이 `android-data-models`(Entity→VO→UiState·Gson nullable+기본값·`@Stable` 규칙)와 어긋남이 없는지 확인했는가.
   - 일반론이 아니라 **이 프로젝트 컨벤션 위반**으로 판정 근거를 적었는가. SSOT가 설치돼 있는데 읽지 않은 채로 확정하지 않았는가. (부재로 폴백한 경우 그 사유·한계가 리포트에 명시됐는가.)
